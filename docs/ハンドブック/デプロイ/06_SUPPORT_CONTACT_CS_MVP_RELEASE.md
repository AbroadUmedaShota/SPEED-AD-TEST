# サポート問い合わせCS運用MVP 反映・移行手順

## 1. 適用範囲とゲート

[仕様](../../画面設計/仕様/25_support_contact_cs_operations_mvp.md)と[確認者GAS README](../../../99_backend-docs/10_support-contact/viewer-gas/README.md)に対応する、既存確認アプリの更新手順。基点はローカル実装 `224266e2fc3d00c56f77f1a824a8091414ada18b`。本書を含む最終候補SHAは引渡し報告で固定し、そのSHAを独立レビューする。

2026-09-04時点ではローカル準備のみ。実環境の参照・変更、push、PR、merge、GAS反映、AWS操作、メール送信は実施していない。本書は実行許可ではなく、準備完了も本番受入完了を意味しない。

対象は確認者GAS、受付シート末尾12列、履歴シートのみ。公開投稿GAS、サイト、通知先、トークン、Drive添付、権限は変更しない。DB整理・残添付削除関数は移行にも受入試験にも使用しない。

1. ローカル差分・テスト・独立レビューを確定する。
2. 別承認後、対象環境を読み取り確認して下表を埋める。
3. バックアップ、GASソース反映、明示移行、既存デプロイ更新の対象・順序・停止条件を承認する。
4. 限定受入に必要なテストデータ更新を別途承認する。投稿フォームからのメールを伴う試験はさらに別承認とする。
5. 実施結果と未達を確認して運用開始を判断する。

共有トークンの履歴は `actor_identity=shared-token` / `actor_auth_mode=shared_token`。Sessionメールは参考情報で、担当者や本人の個人認証監査を証明しない。画面の注意表示を保持し、個人別監査が必須なら今回の方式のまま運用開始しない。

### 正規列

受付の先頭17列は公開投稿GASが位置指定で書き込むため、並べ替えない。

```text
submission_id, submitted_at, contact_type, name, email, subject, message,
attachment_count, attachment_refs, source_url, user_agent, storage_status,
mail_status, handled_status, handled_by, handled_at, internal_note
```

受付の追加12列は18列目以降に次の順で補う。既存の一部追加済み状態もこの順の先頭連続部分だけを事前確認で許可する。受付ヘッダーの移行実装は「名前の不足分を末尾追加」であり、順序や重複を自動修正・完全検証するものではない。

```text
assignee_email, urgency, case_category, gmail_thread_url, progress_note,
handoff_to, handoff_status, resolution_code, resolution_summary,
next_followup_at, closed_at, closed_by
```

履歴 `contact_case_events` は次の11列。通常更新は全列の完全一致が必須。移行のみ空シート、未作成、または正規の先頭連続部分を補完できる。既存データを並べ替えない。非正規スキーマはpreview/executeのバックアップ作成前、通常履歴追記前に拒否する。

```text
event_id, submission_id, event_type, from_value, to_value, note,
actor_identity, actor_email, actor_auth_mode, request_id, created_at
```

## 3. 承認後の反映順序

以下は未実施。各段階で期待結果が違えば次へ進まない。エラー後の自動再実行は禁止する。

### A. 保全とソース反映

1. 利用者のCS編集を停止し、移行前の受付ID集合・状態・更新日時・行数・全ヘッダーと既存履歴件数を閲覧制限付きで記録する。行番号だけを識別子にしない。
2. 承認された方法でSpreadsheet全体を保全し、受付と既存履歴を含むこと、アクセス制限、コピーの読み取り可能性を確認する。Drive添付本体の複製はこの移行に含まれない。
3. 現行公開バージョンのソースと設定の参照を保全する。ソースpushもエディタHEADやテストデプロイへ影響する変更なので、対象承認後のみ実施する。
4. 承認済み最終候補の確認者GASだけを既存プロジェクトへ反映する。この段階では公開Web Appバージョンを更新しない。公開受付GAS、トークン、URL、アクセス方式は変えない。

### B. 明示移行

1. 許可されたApps Script実行ユーザーで `previewContactCaseSchemaMigration()` を呼ぶ。認証ガード付きであり共有トークン経由の実行入口は作らない。
2. 戻り値 `missingHeaders`、`eventSheetExists`、`missingEventHeaders`、`legacyCompletedSubmissionIds` を事前照合結果と比較する。previewはtimezoneや全件数を返さないため別の事前確認を省略しない。受付IDを共有ログへ転記しない。
3. 不足も未移行の対応済み行もない場合は不要なexecuteをしない。executeを再実行するとバックアップが追加作成される。
4. 実行承認後だけ `executeContactCaseSchemaMigration('PREPARE_CONTACT_CASE_SCHEMA_V1')` を呼ぶ。エディタの通常Runは引数を渡せないため、承認済み呼出方法の確認を事前条件とする。呼出方法未確定なら停止し、一時HTTP入口・トークン入口・API公開を追加しない。
5. 実装は受付シートを `copyTo` で同一Spreadsheet内へ複製し、`contact_submissions_backup_YYYYMMDD_HHMMSS` と命名してから不足列・履歴を追加する。同名時は連番。命名日時はscript timezoneであり、業務日の判定基準とは別。
6. **自動バックアップは受付シート1枚だけ**。既存履歴シートやSpreadsheet全体のバックアップではないためAの保全を代替しない。作成/命名エラー時は途中のコピーが残る場合もあるので、状態を確認して停止する。
7. 正規29列・11列、既存列値/状態不変、バックアップ存在、`legacy_migrated` が対象の対応済みIDごとに1件であることを照合する。実行結果の件数だけで完了にしない。移行中の新規受付IDは別枠で確認し、行数増加を消して帳尻を合わせない。
8. 再previewで不足列・未移行対象が0であることを確認する。移行関数は全体トランザクションでも移行専用ロック付きでもない。部分成功や途中例外では現状保全し、再実行可否を判断者へ戻す。

#### 引数付き実行の具体案（未承認・今回は実行しない）

既存の承認済み呼出方法がない場合は、次の管理用ラッパーを**承認後にだけ**Apps Scriptエディタへ一時追加し、エディタから1回実行して除去する案を使う。これは手順例であり、リポジトリのGASソースには追加しない。

```javascript
function runContactCaseSchemaMigrationOnce_() {
  var result = executeContactCaseSchemaMigration('PREPARE_CONTACT_CASE_SCHEMA_V1');
  console.log(JSON.stringify({
    ok: result.ok,
    backupSheetName: result.backupSheetName,
    addedHeaderCount: result.addedHeaders.length,
    addedEventHeaderCount: result.addedEventHeaders.length,
    migratedLegacyCompletedCount: result.migratedLegacyCompletedCount
  }));
}
```

1. 呼出前に、この一時ソース編集・1回の移行実行・除去を含む承認と実行者を確認する。公開Web Appは旧版のままにする。ラッパーをバージョン化・公開しない。
2. 管理者が対象プロジェクト、既存ソースとの差分、最新preview、全体保全、CS編集停止を再確認する。エディタでラッパーを選択可能であることを確認できなければ実行せず停止する。
3. ラッパー名は末尾underscoreとし、HTMLの `google.script.run`、`doGet`、`doPost`、トークン、時限トリガー、API実行用デプロイからの入口を追加しない。ラッパー内でも既存の許可実行ユーザー確認・確認文字列検証を通す。認証ガードは削除・置換しない。
4. 実行結果は件数とバックアップ名だけを閲覧制限された実行ログで確認する。設定値、トークン、受付ID集合、本文、操作者メールをログ追加しない。例外・結果不明なら再実行せずB7/B8の現状照合へ戻る。
5. 成功・失敗いずれでも、状態調査に必要な記録を保全してからラッパーだけを除去する。他者の編集がないことを確認し、エディタソースが承認済み最終候補に再一致し、一時入口が残っていないことを確認するまでバージョン作成・デプロイを禁止する。

### C. バージョン反映と限定受入

1. 事前確認・移行後照合・独立レビューがすべて通った最終ソースだけをバージョン化する。承認された既存デプロイIDの公開バージョンを更新し、新URLを発行しない。
2. 設定・公開版・ソースの対応を確認する。意図せず権限やスコープが変わる場合は停止し、承認画面を機械的に進めない。
3. トークンなし/不正時の無効表示、一覧・詳細・履歴読み取りを確認する。新MVPの読み取りはmigration/writeを起動しない。認証拒否はDB参照より前であることをローカル証拠と合わせて確認する。
4. 有効な既存認証は秘密値を表示・記録しない承認済み手順で使用する。共有URL・画面キャプチャ・ログへ秘密値を含めない。
5. 別途承認された限定テスト案件だけで、通常保存で状態不変、6状態、必須条件、担当、次回日付、引継ぎ、履歴、再送重複防止、競合拒否を確認する。PC/390px、クリック/Enter、添付表示、共有トークン注意表示も確認する。
6. 更新失敗・結果不明時は一覧を再取得して案件と履歴を照合し、連打や新request IDでの再試行をしない。履歴に残った受入操作は削除せず、テスト案件の扱いを承認事項として残す。
7. 本手順の限定受入はメールを送信しない。公開フォームによる保存・WEBP・通知の回帰確認は別の送信承認とテストモード宛先限定確認がある場合だけ実施する。未実施なら未確認として報告する。

## 4. 中止・切り戻し

| 発生段階 | 対応 |
| --- | --- |
| 事前照合不一致 | 書き込まず停止。対象・スキーマ・所有者・timezone・承認を解決する |
| ソースだけ反映済み | 現行公開版は維持。エディタHEAD復元にも別承認が必要。他者の未反映変更を上書きしない |
| 移行途中/照合失敗 | 新UIを公開しない。受付・履歴・コピーを現状保全し、差分をID単位で照合。全体復元/列削除/イベント削除をしない |
| 新版公開後、CS編集開始前 | 編集を止め、承認済み直前デプロイ版へ戻す判断が可能。追加列・履歴は維持し、旧版の表示/読み取り副作用を確認してから利用再開 |
| CS編集開始後 | 先に編集停止。新2状態、進捗、引継ぎ、結果、日付、履歴を保全。旧4状態UIは新状態を安全に表示・編集できず、未対応選択や対応中対象からの除外が起こり得る。旧版復帰だけでは編集再開不可 |

旧版は新しい `progress_note` と旧 `internal_note` の同期も保証しない。旧版読み取りにはヘッダー補完処理があるため「旧版へ戻せば読み取り専用」とも扱わない。CS開始後の切り戻しは、新状態を未対応へ一律変換せず、案件ID・更新日時・イベント履歴を用いる個別復旧案を承認してから行う。

移行バックアップで受付シート全体を上書きすると、移行後の新規投稿や対応記録を失う。**全データ巻き戻しは禁止**。本移行は追加型だが、公開版の切り戻しと業務データの復旧は別作業であり、自動的・完全に可逆ではない。列・履歴・添付・検証投稿を削除する操作は本手順の範囲外。

## 5. ローカル検証と引渡し証拠

対象環境はWindows/PowerShell、Node。以下のコマンドを最終候補で実行し、exact SHAと結果を引渡し報告へ記録する。

```powershell
node --test tests/support-contact-contract.test.mjs
$previousTz = $env:TZ
try {
  $env:TZ = 'UTC'
  node --test tests/support-contact-contract.test.mjs
  $env:TZ = 'America/Los_Angeles'
  node --test tests/support-contact-contract.test.mjs
} finally {
  $env:TZ = $previousTz
}
node --test tests/survey-sample-defaults.test.mjs
node --check tests/support-contact-viewer-mock-server.mjs
git diff --check
```

- 契約テストは既存22件に非正規履歴schemaの副作用前拒否、正規prefix補完/既存列維持の2件を追加した24件。通常・UTC・Los Angelesで日付境界、Dateセル、無効日付、認証前DB未参照、クリック保存時の状態維持、競合・再送・復元を確認する。
- GASはNodeの `new Function` で構文確認し、Index.htmlのインラインscriptはGASテンプレート置換後に同様に確認する。これは実GAS権限/API実行の証明ではない。
- 基点 `224266e` の独立レビューはPASS、UTC/LA各22件とdiff確認済み。合成ChromeのPC/390pxで通常保存・Enter・クイック操作・日付維持を確認済み。ただし独立レビュアーはブラウザ検証を再実行していない。
- 今回追加した履歴schema修正と本手順は別の最終独立レビュー対象。基点のPASSを流用して受入済みにしない。実Google環境、複数利用者の実認証、Firefox/Edge/Safari、実メール配送は今回未確認。
- テスト実行は有料CIを起動しない。合成データ以外の記録・秘密値を証跡に含めない。
