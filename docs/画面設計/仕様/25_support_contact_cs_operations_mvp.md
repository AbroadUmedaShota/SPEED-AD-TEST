# お問い合わせ確認アプリ CS運用拡張MVP

## 1. 目的

既存の問い合わせ確認アプリを、問い合わせの閲覧だけでなく、CS担当者が受付からクローズまでの進行状況を共有できる最小限の案件管理画面へ拡張する。

対象フローは次のとおりとする。

`受付 -> 情報確認 -> 分類 -> CS判断 -> 返信または引継ぎ -> 結果確認 -> 記録 -> クローズ`

本書はMVP検討用の草案であり、GAS、Spreadsheet、本番環境、外部メール送信の変更を承認するものではない。公開フォーム仕様は `23_support_contact_form_requirements.md` を正とする。

## 2. 現在地

### 2.1 現行構成

| 領域 | 現行 |
| --- | --- |
| 公開フォーム | `https://support.speed-ad.com/contact/` |
| 投稿受付 | 公開投稿専用Google Apps Script |
| 問い合わせ正本 | Google Spreadsheet `contact_submissions` |
| 添付 | Google Drive。Spreadsheetには参照ID/URLを保存 |
| 社内通知 | Gmail。通知本文から確認アプリ詳細へ遷移 |
| 確認画面 | 公開投稿GASと分離した確認者専用Apps Script Web App |
| 認証 | 通知URLの共有アクセストークン。アカウント単位認証ではない |

### 2.2 現行機能

- 問い合わせ一覧、詳細、添付プレビュー
- `未対応`、`対応中`、`対応済み`、`保留`の状態更新
- 内部メモ、最終更新者、最終更新日時
- 返信メール作成リンク
- 未保存状態の離脱確認

### 2.3 不足しているCS運用機能

- 担当者、緊急度、問い合わせ分類
- 顧客回答待ち、引継ぎ待ちなどの進行状態
- 引継ぎ先と引継ぎ受領の記録
- 上書きされない対応履歴
- クローズ条件と対応結果
- Gmailスレッドへの参照
- 担当者変更や滞留を知らせる通知ルール

## 3. MVP範囲

### 3.1 対象

- `support.speed-ad.com/contact/` から受け付けた問い合わせ
- CS担当者による分類、担当、進行状態、引継ぎ、結果、クローズの記録
- Gmailで行った返信への参照リンク
- 一覧での担当者、状態、緊急度、滞留状況の確認

### 3.2 対象外

- Gmail本文や添付の自動取り込み
- アプリからのメール自動送信、Chatwork/Teamsへの自動投稿
- 電話、営業アウトバウンド、問い合わせフォーム外案件の自動収集
- SPEED AD Laravel本体のユーザー、契約、請求データの更新
- 回答本文、名刺画像、OCR情報との自動連携
- 任意のSpreadsheet編集、全件CSV出力

電話・Gmail起点の案件登録、営業アウトバウンド管理は、問い合わせフォーム運用が安定した後の別フェーズとする。

## 4. MVP項目

| 項目 | 形式 | 要件 |
| --- | --- | --- |
| 担当者 | 許可済みメールアドレス | 未割当を許可。自由入力は不可 |
| 状態 | 固定選択 | `未対応`、`対応中`、`顧客確認待ち`、`引継ぎ待ち`、`保留`、`対応済み` |
| 緊急度 | 固定選択 | `高`、`中`、`低`。初期値は問い合わせ種別にかかわらず`中` |
| 分類 | 固定選択 | `操作案内`、`不具合`、`契約・料金`、`導入相談`、`要望`、`その他` |
| Gmailリンク | URL | `https://mail.google.com/mail/` 配下の参照URLのみ。本文は保存しない |
| 進捗メモ | テキスト | 最新状況の要約。顧客へ送る文章の正本にはしない |
| 対応履歴 | 追記専用 | 状態、担当者、引継ぎ、メモ変更を時刻・操作者付きで記録 |
| 引継ぎ先 | 固定選択 | `CS`、`営業`、`開発`、`管理者`、`その他` |
| 引継ぎ状態 | 固定選択 | `なし`、`依頼済み`、`受領済み`、`差戻し` |
| 対応結果 | 固定選択+要約 | `解決`、`案内完了`、`引継ぎ完了`、`対応不要`、`継続対応` |
| 次回確認日 | 日付 | 顧客確認待ち、保留、継続対応時に設定 |
| 通知要否 | 固定状態 | MVPでは通知対象を画面表示するだけ。自動送信は別ゲート |

担当者候補は `CONTACT_VIEWER_EMAILS` から取得する。現行の共有トークンは候補者の表示・選択を許可するだけであり、実際の操作者をそのメールアドレスとして認証するものではない。

顧客確認待ち、保留、継続対応の次回確認日は必須とし、保存日より前の日付は受け付けない。

`next_followup_at` は時刻を持たない `YYYY-MM-DD` とし、日付文字列をUTC日時へ変換しない。SpreadsheetからDateセルを取得した場合は、そのSpreadsheetの `getSpreadsheetTimeZone()` を指定して日付へ戻す。「本日」と期限超過・クローズ時の期限判定にも同じタイムゾーンを使う。空値は空として扱い、不正な暦日は保存時に拒否する。

確認者GASの `appsscript.json` は `Asia/Tokyo` だが、シートのタイムゾーンと一致するとは仮定しない。本実装ではDateセルの正本であるシート側を優先し、取得不能時に別タイムゾーンへ黙って切り替えない。本番シートの実設定値は今回未確認であり、移行プレビュー前の読み取り確認項目とする。Googleも両設定が別である点を明示している。[Spreadsheet API](https://developers.google.com/apps-script/reference/spreadsheet/spreadsheet#getSpreadsheetTimeZone())、[Session API](https://developers.google.com/apps-script/reference/base/session#getScriptTimeZone())。

## 5. 状態遷移とクローズ条件

```text
未対応
  -> 対応中
  -> 顧客確認待ち / 引継ぎ待ち / 保留
  -> 対応中
  -> 対応済み
```

`対応済み`へ変更するには、次をすべて満たす。

1. 担当者が設定されている。
2. 対応結果が設定されている。
3. 進捗メモまたは対応履歴に最終対応が記録されている。
4. 引継ぎがある場合は`受領済み`または`引継ぎ完了`である。
5. 顧客確認待ち、保留、継続対応の場合は次回確認日が未経過で放置されていない。

既存の`対応済み`データは移行時に再判定せず、`移行済み`の履歴イベントを1件追加して維持する。

## 6. 保存モデル

既存の`contact_submissions`は受付内容と最新状態の正本として維持し、CS運用列を追加する。対応履歴は上書き防止のため別シート`contact_case_events`へ追記する。

### 6.1 `contact_submissions`追加候補

- `assignee_email`
- `urgency`
- `case_category`
- `gmail_thread_url`
- `progress_note`
- `handoff_to`
- `handoff_status`
- `resolution_code`
- `resolution_summary`
- `next_followup_at`
- `closed_at`
- `closed_by`

### 6.2 `contact_case_events`

- `event_id`
- `submission_id`
- `event_type`
- `from_value`
- `to_value`
- `note`
- `actor_identity`
- `actor_email`
- `actor_auth_mode`
- `request_id`
- `created_at`

履歴にはフォーム本文、メール本文、添付内容、トークンを複製しない。

## 7. 権限・個人情報・監査

- 公開投稿GASは案件管理列と履歴を更新できない。
- 確認者GASだけが許可済みの固定操作を実行する。
- ブラウザから列名、シート名、任意式、任意操作を指定させない。
- Gmailリンクは許可済みホストを検証し、画面表示時は`noopener noreferrer`を付ける。
- MVPのGASはGmailリンクが `https://mail.google.com/mail/` で始まることだけを検証する。数値プロファイルを含むURLからWorkspace所属は判定できない。リンク先メールの閲覧可否はGoogle側のログインアカウントと権限に従い、確認アプリは本文を取得しない。
- 状態、担当者、引継ぎ、クローズ変更は必ず履歴へ追記する。履歴書込みに失敗した場合は本体更新も成功扱いにしない。
- 更新時は画面取得時の `handled_at` を期待リビジョンとして照合し、不一致では保存せず再読み込みを求める。同一 `request_id` の再送は履歴と案件行を重複更新しない。
- 現行の共有トークン方式は利用者個人を確実に識別できない。担当者別監査を本運用要件とする前に、Googleアカウント単位認証または同等の認証へ移行する。
- 共有トークン運用中の履歴は `actor_auth_mode=shared_token` とし、Sessionからメールアドレスが取得できても参考表示に限定する。`actor_identity` は認証主体を示すが、個人監査の証拠として扱わない。
- 個人情報を含む問い合わせ本文、添付、Gmailリンクは既存の許可利用者だけに表示する。

## 8. 通知方針

MVPの初期リリースでは自動メール送信を追加しない。次の条件を画面上の`要確認`として表示する。

- 高緊急度で未割当
- 未対応のまま所定時間を超過
- 次回確認日を超過
- 引継ぎ依頼済みのまま未受領

未対応の滞留時間は `CONTACT_UNHANDLED_STALE_HOURS` で設定する。業務上の閾値が未承認の間は未設定とし、未対応滞留だけは判定しない。高緊急度未割当、次回確認日超過、引継ぎ未受領はこの設定に依存せず表示する。

通知メールやTeams/Chatwork連携は、宛先、重複防止、再送、送信失敗、監査、停止手順を確定した別リリースで追加する。

## 9. 移行とロールバック

- 一覧・詳細の読み取りではSpreadsheetを変更しない。明示移行関数の実行時だけ、`contact_submissions` の既存列順と既存値を変更せず、不足列を末尾へ追加する。
- 公開投稿GASが書き込む既存17列は順序を固定し、CS運用列は18列目以降に置く。公開投稿GASは新規行の既存17列だけを書き込み、CS運用列を更新しない。
- 空の `handled_status` は表示時だけ `未対応`、空の `urgency` は表示時だけ `中`、空の `handoff_status` は表示時だけ `なし` として扱う。初回保存まで既存行へ値を書き戻さない。
- 既存4状態 `未対応`、`対応中`、`保留`、`対応済み` はそのまま有効とする。
- 履歴シート `contact_case_events` は明示移行関数の実行時に作成し、既存問い合わせ本文、添付、トークンは複製しない。移行未実施の通常更新は拒否する。
- 履歴は正規11列の順序・一意性を検証する。通常更新は完全一致、移行は未作成・空シート・正規の先頭連続部分だけを許可し、不足末尾だけ補う。列入替・重複・未知列・途中欠落は副作用前に拒否し、既存列を並べ替えない。
- 案件行は1回の範囲更新、履歴は1回の範囲追記で保存する。履歴追記の例外時は更新リクエストIDで結果を確認し、履歴が保存済みなら案件行を維持する。未保存を確認できた場合は更新前へ戻し、復元値を照合して成功を返さない。保存結果が不明または復元不能なら手動確認を要求する。
- 本番移行前に別承認でSpreadsheet全体を保全する。移行関数が自動複製するのは受付シートだけであり、既存履歴のバックアップを代替しない。列・履歴は切り戻し時も削除しない。
- CS編集開始後は新2状態や進捗を旧版が安全に扱えないため、編集停止と現状保全を先に行い、直前版復帰だけで編集再開しない。状態の一律変換や全体バックアップ上書きで移行後の新規投稿を消す復旧は禁止する。個別復旧は別承認とする。
- 反映順序、実環境未確認項目、中止条件、限定受入、切り戻しは[反映・移行手順](../../ハンドブック/デプロイ/06_SUPPORT_CONTACT_CS_MVP_RELEASE.md)を正本とする。

## 10. 変更ゲート

| ゲート | 完了条件 |
| --- | --- |
| 仕様 | 状態、分類、緊急度、担当者一覧、引継ぎ先、クローズ条件をCS責任者が承認 |
| ローカル | 合成データで一覧、詳細、更新、履歴、必須条件、レスポンシブを確認 |
| GAS | 既存受付処理を変更せず、固定更新APIと追記専用履歴を追加。テストモードで確認 |
| データ | 既存列バックアップ、追加列、履歴シート、ロールバック手順を確認 |
| 本番 | 外部送信なしで既存許可ユーザーによる限定受入後、別承認で反映 |

## 11. 直近の実行項目

1. CS責任者と状態・分類・緊急度・クローズ条件を確定する。
2. ローカル実装・合成データ試験・移行手順の最終候補を独立レビューする。本番受入とは区別する。
3. 別承認後に対象GAS・現行列・Spreadsheet timezone・バックアップ・移行呼出方法を確認し、明示移行と既存Web App更新の実行可否を判断する。
4. アカウント単位認証へ移行するまでの暫定利用者と監査上の制約を承認し、外部送信を伴わない限定受入範囲を確定する。

## 12. 受入条件

- 現行フォーム投稿、Sheet保存、Drive添付、社内通知、受付メールを壊さない。
- 担当者、状態、緊急度、分類、引継ぎ、結果、次回確認日を確認できる。
- 主要変更が追記専用履歴に操作者・日時付きで残る。
- クローズ必須条件を満たさない案件を`対応済み`にできない。
- メール本文、外部送信、Laravelデータ更新を行わない。
- モバイルとデスクトップで一覧から詳細、更新、履歴確認まで操作できる。
