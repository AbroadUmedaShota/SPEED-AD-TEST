# CSオペレーターアプリ MVP実装パッケージ

## 1. 目的と判断境界

Cloudflare D1を採用する方針と、ローカルD1/workerdで確認済みの原子性契約を、次のMVP実装へ接続する。`Q-CONTACT-003`により本書のローカルMVP範囲と4業務ルールは承認済み。Cloudflare資源、認証、費用、実データ、本番連携の作成・変更は承認に含まれない。

初回MVPは、CS担当者が合成案件について次の4場面を一つの画面で完了できることを到達点とする。

1. 未割当案件を見つけて担当する。
2. 対応内容をメモとして記録する。
3. 顧客返信または社内確認を待つ。
4. 解決し、必要な場合は再開する。

## 2. 確定済み要件

- 専用DBはCloudflare D1を採用する。
- 初期利用者は少人数の許可担当者に限定する。個別アカウントと公開先は共有試用環境作成時に確定する。
- 許可された全担当者が全案件を閲覧・更新できる。案件の担当者は責任者表示と絞り込みに使い、アクセス制御には使わない。
- 案件更新、追記専用履歴、冪等受付を同じD1 `batch()`で扱う。
- 更新は`expectedVersion`を必須とし、古い版の更新を拒否する。
- 同じ`requestId`と同じ内容の再送は最初の受付結果を返し、履歴を重複させない。同じIDで異なる内容は拒否する。
- 操作者はブラウザーの入力値ではなく、信頼済み認証アダプターが確定する。
- 公開問い合わせフォーム、現行GAS、Spreadsheet、Drive、通知は、本番移行が承認されるまで変更しない。
- 合成データだけを使用し、実顧客情報をローカルMVPへ持ち込まない。

## 3. 初回仕様の承認内容

初回実装では次の判断についてAを採用済みとする。

**判断:** ローカルMVPを、状態・メモ中心の最小版と4場面の操作改善版のどちらで作るか。

| 選択肢 | 内容 | 影響 |
| --- | --- | --- |
| A: 推奨 | 既存6状態を維持し、4場面ごとの操作と条件入力を実装 | 状態の互換性を維持しながら、待ち条件や解決根拠を同じ操作で記録できる。固定APIは8操作必要 |
| B: 最小 | 6状態の選択、担当変更、メモ追記だけを実装 | 実装量は少ないが、次の対応、確認予定日、解決根拠が別入力または自由記述になり、CS試用で確認したいUXを評価できない |

採用理由は、追加するのが状態値ではなく既存状態へ安全に到達する操作と必須入力であり、D1の原子性契約を実業務の縦断シナリオで確認できるためである。

### 3.1 推奨: 既存6状態を保持し、4場面向けの操作UIを採用する

保存する状態値は変更しない。画面表示だけをCS担当者が判断しやすい表現にする。

| 保存値 | 推奨表示 | 主な操作 |
| --- | --- | --- |
| `未対応` | 新規 | 自分を担当にする、対応を始める |
| `対応中` | 対応中 | メモを残す、待ちにする、保留、解決 |
| `顧客確認待ち` | お客様の返信待ち | メモを残す、対応を再開する |
| `引継ぎ待ち` | 社内確認待ち | メモを残す、対応を再開する |
| `保留` | 保留 | メモを残す、対応を再開する |
| `対応済み` | 解決済み | 対応を再開する |

この案なら既存値との互換性を維持しながら、汎用的な状態選択ではなく業務操作から必要項目を提示できる。状態値の一括変換、新しい状態、SLA、自動通知は追加しない。

### 3.2 操作と入力

| 操作 | 必須入力 | 状態更新 | 履歴 |
| --- | --- | --- | --- |
| 自分を担当にする | なし | 状態は維持 | 担当変更を記録 |
| 対応を始める | 担当者が設定済み | `対応中` | 開始を記録 |
| メモを残す | メモ、1〜4000文字 | 状態は維持 | メモを追記 |
| お客様の返信を待つ | メモ、次の対応、確認予定日 | `顧客確認待ち` | 待ち条件を記録 |
| 社内へ確認する | 確認先、依頼内容、次の対応、確認予定日 | `引継ぎ待ち` | 確認条件を記録 |
| 保留する | 保留理由、再開条件、確認予定日 | `保留` | 保留条件を記録 |
| 解決する | 対応結果、最終対応メモ | `対応済み` | 解決内容を記録 |
| 対応を再開する | 再開理由 | `対応中` | 過去の解決情報を残して再開を記録 |

次の対応は200文字以内、確認予定日は日付として本日以降を許可する。確認予定日を迎えても自動で状態を変えず、メールや外部通知も送らない。

社内確認先は`CS`、`営業`、`開発`、`管理者`、`その他`の固定候補とし、自由入力値は保存しない。`その他`の具体的な確認先は、同じ操作で必須となる依頼内容へ記録する。

### 3.3 変更が必要な業務ルール

初回MVPで新たに合意が必要なのは次の4点だけとする。

1. 待ち・保留では、責任者、次の対応、確認予定日を失わない。
2. 解決には担当者、対応結果、最終対応メモを必須とし、未完了の待ち条件を黙って消さない。
3. 再開では理由を必須とし、過去の解決日時・結果は履歴に残す。
4. 訂正は履歴の上書きや削除ではなく、訂正メモの追記で扱う。

分類、優先度、アーカイブ、通知、SLA、返信送信は既存ルールを変更せず、初回MVPの合否にも含めない。

## 4. 実装範囲

### 4.1 UI

- 入口は`自分の対応`、`未割当`、`本日確認`、`すべて`の4つ。
- 一覧は件名、投稿者、状態、担当者、確認予定日を表示する。
- 詳細は問い合わせ本文と添付を先に表示し、直近メモ・履歴、操作入力を続けて配置する。
- 959px以下は一覧と詳細を一画面ずつ表示し、戻った際に検索・絞り込み・選択位置を復元する。
- 入力不備、競合、認証切れ、保存失敗でも未保存入力を保持する。
- 一覧対象から外れる更新後も詳細を勝手に閉じない。

### 4.2 固定API

任意列更新を許可する汎用`PATCH`は作らず、次の固定操作だけを公開する。

- `GET /api/cases`
- `GET /api/cases/:caseId`
- `GET /api/cases/:caseId/events`
- `POST /api/cases/:caseId/actions/assign-self`
- `POST /api/cases/:caseId/actions/start`
- `POST /api/cases/:caseId/actions/note`
- `POST /api/cases/:caseId/actions/wait-customer`
- `POST /api/cases/:caseId/actions/wait-internal`
- `POST /api/cases/:caseId/actions/hold`
- `POST /api/cases/:caseId/actions/resolve`
- `POST /api/cases/:caseId/actions/reopen`
- `GET /api/attachments/:attachmentId/content`

すべての更新APIは`requestId`と`expectedVersion`を要求する。成功時は不変の受付結果を返す。競合時は現在版を返し、クライアントが最新内容と下書きを比較できるようにする。

### 4.3 D1 schema

| テーブル | 責務 |
| --- | --- |
| `contact_cases` | 受付内容、現在状態、担当、次の対応、確認予定日、版、アーカイブ情報 |
| `contact_case_events` | 操作単位の追記専用履歴。本文・添付・秘密値は複製しない |
| `contact_api_requests` | request ID、payload hash、不変受付結果による冪等制御 |
| `contact_operators` | 許可担当者、表示名、有効/無効。認証方式そのものは保持しない |
| `contact_attachments` | 案件と非公開オブジェクトの参照、MIME、サイズ、hash |

検索・一覧用に状態、担当者、確認予定日、受付日時のインデックスを用意する。本文、全履歴、画像は一覧で取得せず、詳細表示時に遅延取得する。

### 4.4 認証境界

ローカル版は合成操作者を返す`TrustedPrincipalResolver`を使用する。共有版では同じinterfaceを実認証アダプターへ交換し、署名、issuer、audience、有効期限、許可担当者をサーバー側で検証する。

共有試用の認証方式は未決であり、Cloudflare Access、Google IdP、メールOTPのいずれも採用済みとして実装しない。共有文字列だけで個人を識別する方式は採用候補にしない。

認証切れでは、サーバーはrequest bodyを解釈する前に更新を拒否し、入力内容をレスポンスやログへ複製しない。クライアントは未保存入力を現在タブのメモリだけに保持し、`localStorage`、`sessionStorage`、URLへ保存しない。再認証後は案件の最新版と権限を取得し直し、利用者が内容を確認して明示的に再送する。自動再送はしない。ログアウト、タブ終了、担当者無効化時の永続復元は保証せず、機密入力を端末へ残さないことを優先する。

### 4.5 添付境界

ローカル版は合成画像を扱う`AttachmentStore`を使用し、API経由以外で参照できない契約を検証する。共有版の保存先は未決であり、非公開R2または既存Drive継続をQ-CONTACT-002で判断する。

添付APIは、認証・案件アクセス・attachment IDとcase IDの関係を検証してから返す。object key、Drive ID、署名URLを一覧レスポンスへ含めない。

### 4.6 migrationとrestore

- ローカル: migrationを空DBへ適用し、合成seedを投入して再現できるようにする。
- migration: 版番号を持ち、適用前後のschemaを検証する。手編集で本番schemaを変更しない。
- ローカル復元: エクスポート相当のfixtureから別の一時DBへ戻し、案件件数、版、履歴連続性、添付hashを照合する。
- 共有試用: 別検証DBへの復元試験を完了条件にする。実資源作成後に具体的なexport/restoreコマンドを確定する。
- 本番: Spreadsheet/Driveの読取り棚卸しと移行リハーサルを別承認で行う。旧新を同時編集せず、切戻し時も新DBで増えた受付・更新を保全する。

## 5. 依存関係

| 項目 | ローカルMVP | 共有試用 | 本番移行 |
| --- | --- | --- | --- |
| D1 | Wranglerのローカルbinding | remote D1資源が必要 | 容量・費用・復旧運用の確定が必要 |
| 認証 | 合成principal | Q-CONTACT-002の方式決定と設定が必要 | 担当者追加・停止手順が必要 |
| 添付 | 合成AttachmentStore | Q-CONTACT-002の保存先決定が必要 | 既存添付の移行・照合が必要 |
| データ | 合成seedのみ | 合成または承認済み匿名fixture | 実データ棚卸しと移行承認が必要 |
| 通知 | なし | なし | 現行通知導線の切替確認が必要 |
| 費用 | 新規外部費用なし | 無料枠・上限・停止時運用の確認が必要 | 継続費用と責任者の確定が必要 |

## 6. 完成条件

### 6.1 ローカル動作完了

- 合成案件で4場面を一巡できる。
- 既存6状態を保持し、操作に応じた必須入力だけが表示される。
- 案件、履歴、冪等受付が原子的に保存される。
- 同時更新、同一再送、異内容のID再利用、保存失敗から安全に復帰する。
- 一覧、詳細、履歴、合成添付、狭い画面、キーボード操作を確認する。
- 空DBからmigrationとseedを再現し、別の一時DBへのローカル復元を確認する。

### 6.2 共有試用完了

- Q-CONTACT-002を決定後、許可担当者と未許可利用者の許可・拒否を実アカウントで確認する。
- 許可された全担当者が全案件を更新でき、操作者が監査履歴へ正しく残る。
- 2端末競合、セッション切れ、利用者無効化、再送を確認する。
- 添付が非公開で、許可されたAPI経由だけで取得できる。
- 別の検証DB・添付保存先へ復元し、件数、版、履歴、hashを照合する。
- 無料枠、費用上限、上限到達時の停止・復旧手順を確認する。

### 6.3 本番移行完了

- 既存SpreadsheetとDriveを読み取りで棚卸しし、移行対象・除外対象・例外を承認する。
- 検証環境で移行リハーサルと件数・ID・本文・添付・状態の照合を完了する。
- 編集停止、差分取込み、正本切替、通知導線、限定受入、切戻しの順序を確定する。
- 本番テストは通知先を限定し、受付から確認までを確認する。
- 新DBで増えた記録を失わずに切り戻せることを確認する。

## 7. 共有前の未決事項 `Q-CONTACT-002`

利用者に必要な判断は、共有試用へ進む直前に次の1件へまとめる。

**判断:** 共有試用の認証と添付保存をどの組合せにするか。

| 選択肢 | 認証 | 添付 | 影響 |
| --- | --- | --- | --- |
| A: 推奨 | Cloudflare AccessとGoogleログインを接続し、メール単位で許可 | 非公開R2 | 同一Cloudflare境界で認証・API・添付を管理しやすい。設定権限、R2利用開始、無料枠と費用上限の確認が必要 |
| B: 最小変更 | 既存Google側の認証方式を継続 | 既存Driveを継続 | 移行量は少ないが、Worker/D1との認証主体・添付権限を二つの運用境界で管理する必要がある |
| C: 試用優先 | Cloudflare AccessのメールOTP | 非公開R2 | Google IdP準備を待たず試せるが、本人確認と日常ログイン体験が本番候補と異なる |

推奨はA。認証済みメールをWorkerで再検証し、D1 allowlistと照合でき、添付も公開URLから分離できるためである。Aを選んでも、資源作成、費用、公開、実アカウント登録は別の実行承認とする。

## 8. 次の一件

次は製品コードへ広げず、既存ローカルデモを保全した別作業領域で、`contact_cases`、`contact_case_events`、`contact_api_requests`、`contact_operators`、`contact_attachments`の正式migrationと固定APIの契約テストを合成データだけで実装する。

最初の縦断シナリオは「未割当案件を自分に割り当て、対応を開始し、メモを1件保存する」。UI、認証、添付の実装前に、各操作の入力、版、履歴、受付結果が一貫することを確認する。外部資源、実認証、費用、実データは使用しない。
